# DentalFlow SaaS implementation plan

**Purpose:** Plan the work required to take the existing DentalFlow clinic
follow-up product toward a public commercial dental-clinic SaaS. This document
is planning only; it does not authorize product changes, migrations, or
production operations.

**Baseline:** The reviewed repository describes DentalFlow as a focused
follow-up workspace, not a full practice-management system. The plan preserves
the existing Next.js 14 App Router, TypeScript, Prisma 6, Supabase Auth,
PostgreSQL, and Supabase Storage stack. It extends the current domain models
and workflows where needed; it does not call for a rewrite or parallel copies
of existing patient, clinic, membership, treatment, appointment, recall,
message, insurance, or finance models.

## How to read the statuses

Statuses reflect repository evidence, not production verification:

- **Complete:** the scoped capability has a repository implementation for
  current needs. This is not a guarantee of commercial or regulatory readiness.
- **Partial:** some of the workflow exists, but important product, operations,
  or verification work remains.
- **Missing:** no implementation was found in the reviewed repository.
- **Unverified:** documentation or code suggests a capability, but deployment,
  integration, or operational behavior was not established by static review.

The source audit did not inspect hosted Supabase/Vercel settings, use live
credentials, execute migrations, or run the test suites. Referenced file paths
are relative to the repository root.

## Small, independently reviewable milestones

Each milestone should be a separate PR with its own acceptance checklist.
Dependencies are explicit; milestones can be paused without requiring a
large-scale rewrite.

1. **M0 — Scope and unknowns register (P1).** Decide product promise (follow-up
   product vs full PMS), target launch cohorts, role policy, billing model, and
   privacy owner. List hosted configuration and legal facts that remain
   unknown. **Exit:** product scope and launch gates have named decision owners.
2. **M1 — Tenant boundary inventory and verification (P0).** Enumerate every
   route, Server Action, repository query/raw SQL, and Storage operation;
   inspect non-production grants/RLS/runtime roles; extend the existing
   two-clinic integration approach. **Exit:** evidence-backed tenant matrix
   passes using production-equivalent roles and is reviewed independently.
3. **M2 — Privacy and recovery requirements (P0).** Complete data-flow/vendor
   inventory, retention/export/erasure requirements, incident plan, backup
   selection, and recovery objectives. **Exit:** approved policies and
   isolated restore exercise plan; no implementation assumptions hidden.
4. **M3 — Operational launch baseline (P0).** Configure monitoring, alert
   routing, support intake/escalation, deployment secrets, and staged release
   gates. The repository now includes a database readiness endpoint, a root
   application error fallback, privacy-conscious timing logs, and an initial
   operator runbook. External alert routing, staffed support intake, backup/
   restore verification, and rehearsed escalation remain deployment-level
   work. **Exit:** synthetic failures alert correctly; support and deploy
   runbooks are rehearsed.
5. **M4 — Clinic access lifecycle (P1).** Define permissions; implement
   invitation, role assignment/removal, and offboarding by extending existing
   `ClinicMembership` and guards. **Exit:** role matrix and revocation tests
   pass; no client-submitted role is trusted.
6. **M5 — Patient privacy lifecycle (P1).** Implement only approved export,
   retention, and erasure behavior across existing patient-linked records,
   message/insurance audit records, and Storage. **Exit:** synthetic-clinic
   export/deletion tests prove scope, traceability, and required exceptions.
7. **M6 — Schedule and ledger invariants (P2).** Keep appointment and visit
   states explicitly independent; finish schedule and financial
   source-of-truth invariants with the smallest compatible changes. The
   appointment workflow now prevents more than one active booking per visit.
   **Exit:** state/concurrency/reconciliation acceptance tests pass with
   existing records preserved.
8. **M7 — Subscription foundation (P0 for charging).** Razorpay-specific
   schema, checkout, webhook processing, owner portal, and initial server-side
   entitlements are implemented as a first slice. Approve provider availability,
   commercial terms, configured plan versions, reconciliation, support, and
   refund policy; exercise the provider test-mode lifecycle before charging.
   **Exit:** verified sandbox lifecycle, tenant-bound reconciliation, and
   outage/cancel/delinquency behavior approved.
9. **M8 — Internal platform support (P1).** Add narrowly scoped, audited,
   least-privilege platform operations after support policy and identity
   controls are approved. **Exit:** ordinary clinic users cannot invoke
   platform operations; elevated access is traceable and revocable.
10. **M9 — Commercial pilot and public rollout (P0 gate).** Run all launch
    gates with a limited clinic cohort; review incidents, support load,
    recovery, billing reconciliation, and privacy requests before increasing
    enrollment. **Exit:** every required launch gate has evidence and a named
    approver.

Milestone priority labels indicate launch sequencing, not a commitment to
implement every optional product capability. In particular, full clinical
charting, insurer integrations, WhatsApp Business messaging, and accounting
integrations require product scope decisions before design or schema work.

## Migration, rollout, and rollback principles

- Keep Next.js 14, TypeScript, Prisma 6, Supabase Auth/PostgreSQL/Storage unless
  a measured constraint demonstrates a specific blocker. No stack change is
  currently justified by the audit.
- Reuse existing domain models. Before introducing a table, field, or entity,
  document why the existing `Clinic`, `ClinicMembership`, `Patient`,
  `TreatmentPlan`, `TreatmentVisit`, `Appointment`, `PreventiveRecall`,
  message, finance, or insurance models cannot represent the requirement.
- Prefer expand/backfill/verify/contract migrations. Do not rename/drop or
  repurpose production columns in the same release that first writes the new
  representation.
- Test migrations on both a clean disposable database and a copy/restore of a
  representative staging database. Confirm index/bucket/policy idempotency
  assumptions before deployment.
- Deploy behind narrow feature flags or cohort configuration when behavior
  can be gated. Make server authorization independent of UI visibility.
- For rollback, disable the feature or revert the application artifact first.
  Do not assume schema rollback is safe after data has been written; use
  forward fixes or a separately reviewed reverse migration. Preserve financial,
  message, insurance, and access audit records.
- Never run integration, migration, or restore commands against production as
  a test. Verify target project identity and obtain explicit migration/recovery
  approval before any production operation.

## Explicit unknowns

- Current production/staging database role, grants, RLS force/policy state, and
  Supabase Storage policy/bucket configuration.
- Actual Vercel or other deployment configuration, CI status, production
  environment variables, Auth redirect settings, and current build health.
- Existing clinic/customer count, data volume, real-data presence, backup tier,
  retention, PITR, storage backup behavior, achieved RPO/RTO, and restore
  readiness.
- Applicable contractual/legal requirements, controller/processor roles,
  permitted data residency, vendor terms, and incident notification duties.
- Commercial plan/pricing, billing provider, trial/grace/cancellation rules,
  entitlement limits, and support SLAs.
- Whether DentalFlow intends to add a full clinical chart/PMS scope, connect to
  insurers, automate WhatsApp delivery, or integrate payment/accounting systems.
- Whether all repository unit and integration tests currently pass; no tests
  or live services were run during the audit used for this plan.
